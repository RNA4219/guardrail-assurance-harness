# 要求の拡張案と着手条件

[要求v0.4](requirements.md)の二つの利用場面を支える拡張案。根拠は[敵対的検証](reviews/requirements-adversarial-20260910.md)。必要性と着手条件の提案であり、実装済み機能や採択済みの開発日程ではない。

## MVP後に具体化した拡張要件

2026-09-15の依頼を受け、[MVP後の拡張要件 v1](productization-requirements.md)にGAH-PR01〜14と対応受入GAH-PAC01〜14を定義した。実案件の有用性・処理速度・導入運用を対象とする。数値は提案目標、製品の14条件は全てNOT_RUNであり、MVPの32/32受入は維持する。

| 順序 | 改修のまとまり | 着手・受入の境界 |
|---|---|---|
| M0 | 実案件の対象/期待結果と性能測定の契約 | 利用許可、対象revision、独立oracle、同条件baselineを固定 |
| M1 | 単体処理とCIの効率化 | 固定通常800試行は中央値30分、全件CI30分を提案。同じ検査と資源上限、総runner時間も評価 |
| M2 | 接続、初回手順、診断、説明、中断回復 | Linux/Windowsの新規利用から選択UCの初回sample結果まで30分を提案 |
| M3 | 2repo・1評価対象でのpilot | 検出と誤通知、保守の実作業時間30%削減を確認。根拠不足なら未実証 |

[拡張仕様 v1](productization-spec.md)で共通入出力と3分冊の詳細へ具体化した。詳細な区間・反復・失敗条件は拡張要件を正本とし、この要約だけで受入しない。M0後にM1/M2の独立部分を並行できる。EX01は実利用集合として具体化、EX03は正常タスク達成率と遅延・費用の観測部分だけを取り込む。EX02の全集合更新、EX03の閾値探索など、残る後期候補を実装済みにしない。[反例レビュー](reviews/productization-requirements-20260915.md)へ対応を記録する。

## MVPへ反映した拡張

| 必要な振る舞い | 要求 | 最小の完成条件 |
|---|---|---|
| 評価契約をcandidateから独立して管理する | GAH-R25 | 契約の無権限変更を拒否し、新旧の条件と採択記録を追える |
| 予定ケースと結果を照合する | GAH-R26 | 重複、欠損、矛盾、再試行、取消しを成功件数へ混ぜない |
| 依存先とCIの適用対象を追う | GAH-R27 | 共有資産の変更・証拠失効と、検査後の対象変更を合格根拠へ反映する |
| 評価データと評価器を校正する | GAH-R28 | 用途・重複・校正失敗を示し、独立性や正しさを過大表示しない |
| 推定の不確かさを判定へ反映する | GAH-R29 | 有限集合の観測と推定を分け、必要な確かさを欠く推定から合格にしない |
| 状態を持つ最小ケースを扱う | GAH-R30 | 単発と二段階の合成ケースで初期状態・途中条件・最終結果を追える |
| データと判定権限を分離する | GAH-R31 | 対象の自己申告や文中の指示で評価契約・権限を変更しない |
| 計画生成から修復確認を分離する | GAH-R32 | 元のFindingと新しい再検証証拠が結び付き、再発を追える |

既存のGAH-R03/R04には、実行中の境界強制、予約分を含む予算、停止確認不能の表示を追加した。MVPの範囲は合成fixture・固定ケースでの評価と計画生成まで。

## 後期候補

以下の優先度は後期候補間の順序案。各候補の採否・oracle・受入水準は着手時に固定する。管理主体は基準管理AI（Control owner）とし、評価運用の役割・実行identity・権限を[初期運用方針](operating-policy.md)に従って設計する。

| ID / 優先 | 拡張と解決する不足 | 着手条件 | 拡張時の受入の方向 |
|---|---|---|---|
| GAH-EX01 / 高 | 利用許可と秘匿処理を確認した実運用由来の評価集合。合成ケースだけでは利用実態の性能を説明できない | R21/R28/R29が成立し、データの利用条件・期待ラベル・母集団・保持を固定できる | 合成/実運用由来を分離し、カテゴリ別の有効範囲と不明を表示する。評価目的の取込みは本番変更権限を含まない |
| GAH-EX02 / 高 | 評価集合更新時の比較。同じ集合を永続利用する限界と、集合変更による比較断絶を扱う | R25/R29が成立し、旧集合・新集合・共通ケースを識別できる | 共通部分の比較と集合構成の変化を分け、共通部分だけの結果を新集合全体の劣化なしにしない |
| GAH-EX03 / 高 | 閾値候補ごとの検出・誤検知・正常タスク達成率・遅延/費用の比較 | R25/R28が成立し、調整用集合と受入用集合を分け、有用性のoracleを定義できる | 有用性の改善と検出性能の低下を同時表示し、提案だけで本番閾値を採択・緩和しない |
| GAH-EX04 / 中 | 長い対話、複数のツール段階、部分/ストリーム出力、多様な入力形式 | R30の最小ケースが成立し、各形式の開始・終了・中断と観測単位を定義できる | 途中の逸脱、観測欠損、未対応形式を区別し、最終出力だけで全セッションを合格にしない |
| GAH-EX05 / 中 | 外部CI・複数実行主体への結果受渡し、署名と失効確認 | R25/R27/R31が成立し、信頼する主体と鍵・署名対象・失効の責任を定義できる | 別対象・別契約・期限切れ・撤回済みの証明を拒否し、署名だけで検査内容の正しさを保証しない |
| GAH-EX06 / 中 | 長期間の変化・カテゴリの偏り・評価器自身の劣化を追う | R28/R29が成立し、観測頻度、必要データ、検出遅延、誤警報の許容範囲を定義できる | 段階的な変化と母集団の変化・欠測・評価器変更を分け、通知欠損も可視化する |
| GAH-EX07 / 低 | 複数の修復案の比較と再検証工数の見積り | R16/R32が成立し、維持する条件・必要証拠・管理主体の確認点を定義できる | 根拠、不足、予測した工数と実績を分け、安価な案を理由に必須検査を削除しない |

専用IAM/OPA等のadapter、運用対象の段階展開・復旧、Web UI、OSCAL連携などの既存構想は要求§2の後期検討として保持する。具体の第三者サービス機能や性能をこの拡張案で検証済みとは扱わない。

## 採否を決める際の共通条件

解決する利用上の問題、対象範囲、入力と期待結果、失敗/不明の扱い、費用・時間・権限、既存要求への影響を揃えてから別Taskへ切り出す。oracleがない項目は探索・設計の対象として残し、架空の合格基準を置かない。MVPの安全条件と比較可能性を緩める拡張は、評価契約の変更として別途扱う。
