# baseline更新の親レビュー

利用者の指示に従い、親が実装・レビュー・検証を担当した。この工程で外部モデルへ委任していない。

## 設計と確認対象

従来は最新baselineの照会と契約が固定したbaselineの照会が同じであり、pointerを移すと過去条件の通常runを検証できなかった。完全参照で保存世代を解決する操作を追加し、保存履歴の整合性と、その根拠の現在有効性を別々に確認する。最新基準を要求する既存baseline_useの意味は維持した。

元Evidenceと比較contextから更新候補を再生成する。採択者と独立validator、期待世代、停止・精算、元の比較baseline、採択時刻、TTLを結合し、採択を同一transactionにした。変更は固定UC-CIのbaseline 1→2とcontract 2に限定した。

世代別の撤回をfilterするだけでは不明な撤回行を見落とすため、系列内の撤回履歴を全て検証してから対象世代への効果を判断する。正常runからの更新、旧基準CIの継続、世代別撤回と依存失効、否定結果の保持、保存失敗のrollback、再起動、既知旧版の明示移行を検証対象にした。

## 検証状態

固定UC-CIの通常runからbaseline generation 1→2への更新を接続した。全体回帰560件の後、保存記録の照合を補正して影響する44件を再検証し、対象全件の成功を確認した。固有の検証対象は561件で、従来551件を保持する。補正後の実Docker248項目も成功し、従来233項目の判定を保持した。固定fixtureの実行92件は全て停止・回収済み。世代ごとの撤回と依存失効、旧基準CIの継続、違反runの昇格拒否、保存失敗時のrollbackを確認した。 補正前の専用9試験と実Docker248項目も保存した。追加レビューでcurrentのdigest破損が提案・検証・採択により見過ごされることを確認し、3操作に更新前currentと採択履歴の照合を追加した。補正後の専用10試験にこの3操作とrollback検査を含める。検証末尾の元baseline照会・撤回だけを、更新後も指定世代へ作用する新APIへ変更した。旧233項目の判定は保持するが、全要求が旧版と同一APIだったとはしない。[工程証跡](../evidence/mvp-baseline-refresh-20260912/README.md)へログとhashを結ぶ。

要求・受入・初期方針と4つの決定例は変更しない。Taskはin_progress、Acceptanceはdraft、release_gate=no_goを維持する。後続契約・条件変更、UC-LLM認証資源、製品監督、保持処理、Finding修復確認と全32受入は残る。
