# 要求明確化の記録

対象は[明確化前の保存稿](../research/archive/before-clarification-20260910/docs/requirements.md)。利用者の要求明確化依頼に基づき、要求案v0.1へ改訂した。

## 具体化した内容

目的と役割、MVP4機能と支援機能、後期機能を分離した。24の要求をIDで識別し、24の受入条件へ対応付けた。元原稿の17機能・14受入項目は[対応表](../requirements-traceability.md)に継承・補強・後期への分離を記録した。

Mutationの検知成功と通常検査の失敗、実行エラー、未到達を区別した。指標の分子分母、0分母、Criticalの欠損、判定優先順、比較可能なbaseline、時点と鮮度、HOLDでも再検査を許すことを要求案にした。技術候補や外部主張を要求根拠から分離した。

## Qwenの補助と親の判断

前回の利用者指示を継続し、DGXの`qwen3.8-flash-next`に要求の曖昧さを問い合わせた。比較条件の同一性、0分母、鮮度の時点、計画の成立、必須/任意、閾値不足、CIとの責務、後期範囲という8観点を参考にした。

Qwenの具体案をそのまま採用していない。鮮度は再収集・実行終了時刻でなく観測時刻を基準とし、計画形式を架空のフラットJSONへ限定せず、閾値を架空の環境変数に固定せず、必須検査を3項目だけに限定しなかった。CIへの返却と本番を止める強制力も分離した。問い合わせ中の暫定案にあった「HOLDで新しい評価を停止」は、必要な診断・再検査を妨げるため採用していない。

[補助記録](../evidence/requirements-clarification-20260910/qwen-assistance.json)。Qwenは独立した承認者ではなく、最終文書はCodexが元原稿と照合した。

## 判断と限界

初期利用場面はcoding agentの開発・CIを仮定した要求案。標準CIでHEALTHYのみ成功とする扱いは運用判断待ちとして残した。Schema/API/CLIの確定、技術選定、外部参照元の変更、製品試験・外部出典検証は行っていない。

要求の機械的な追跡・保存12項目、文書ワークフロー12項目、既存unittest10件が成功した。結果は[技術検収](../acceptance/AC-20260910-04.md)に記録した。対応数の一致は意味の正しさや製品機能の検証を保証しない。
