# MVP後の拡張要件 v1

実案件での有用性、処理速度、導入・運用の容易さを改善するための要件。利用者の2026-09-15の依頼を受け、数値を含めCodexが作成した。**本書作成時点では全14件ともNOT_RUNだった。** その後の実装・検査・製品受入は[現状対応表](productization-status.md)を正本とし、設計時の状態と区別する。 各数値は追加受入の提案目標で、達成済みの性能や外部標準ではない。

[MVPの要求](requirements.md)・[受入条件](acceptance-criteria.md)・[初期運用方針](operating-policy.md)とその契約例は変更しない。MVPの32/32受入・release_gate=goに遡及せず、拡張の成否を別に記録する。[ロードマップ](extension-roadmap.md)、[反例レビュー](reviews/productization-requirements-20260915.md)、[文書作成Task](tasks/TASK.productization-requirements-09-15-2026.md)へ結ぶ。

## 1. 解決する問題と根拠

| 問題 | 確認済みの根拠 | 追加で確かめること |
|---|---|---|
| 実案件への効果が不明 | [最終証跡](evidence/mvp-acceptance-20260913/mvp-final-20260915-summary.json)のUC-LLMは自作合成400ケース・対象2版 | 実際の変更や利用入力で、劣化を発見し、調査・再確認の負担を減らせるか |
| 検査に時間がかかる | [全898試験](evidence/mvp-acceptance-20260913/final-regression-80-summary.json)は同一Windows機の4分割で経過7508.596秒。実Dockerの初回・比較・通常runを含む一連の工程は9993.657秒 | 同じ仕事での単体処理量、通常run、CI全体の待ち時間と総資源を減らせるか |
| 初回に理解する概念が多い | [README](../README.md)・[RUNBOOK](../RUNBOOK.md)・複数の詳細仕様を読み、Docker、identity、契約、baseline、Evidenceを接続する構成 | 新しい利用者・管理AIが一つの手順で初回結果と次の行動に到達できるか |

7508.596秒は単一試験の時間ではなく、9993.657秒は通常800試行だけの時間ではない。[12ジョブ化](evidence/mvp-acceptance-20260913/ci-parallelization-20260915-summary.json)は907件の割当を検査した証拠で、単体性能の改善率を示さない。これらの履歴と、新しく条件を固定して測る性能baselineを区別する。GitHubの現在状態は別途そのSHAのrunを照会する。

## 2. 対象・不変条件

対象はUC-CI（coding agentの開発・CIで制約と検査系の劣化を検知）とUC-LLM（ガードレールの検出性能・誤検知の変化を追跡）の両方。管理主体は生成AIを維持する。変更を作るAI、基準管理AI、validatorの実行identityと権限を分離し、定型運用のたびに人間承認を追加する設計にはしない。

全拡張で次を維持する。各受入は自身の正常例に加え、関係する不成立例も確認する。

- HEALTHY/WARNINGのCI成功方針、Criticalの停止、必須義務100%、欠損・不明・未精算の扱い。必須不足をWARNINGにしない。
- 固定した評価契約・baseline・対象内容・独立oracle、現在の権限・失効・鮮度・依存閉包の再照合。過去の保存結果は現在CIの許可証ではない。
- 校正、全予定と全結果の照合、取消し・停止・資源精算、元Findingと再検証の連結。キャッシュや分割で省略しない。
- 同じ有限集合の観測と母集団の推定を区別する。ラベル不明、未対応、標本不足を成功・正常・ゼロ件へ置換しない。
- 利用許可のある対象・秘匿処理済みデータだけを扱う。外部から届く文章や候補AIの自己申告を、許可・基準変更・採択の命令にしない。
- 非掲載指定のクローズド資産を取得・複製・依存化・同梱せず、名称等も掲載しない。今回の設計根拠は本repoと利用者の要求に限定する。

## 3. 要件と追加受入条件

P0は次期拡張で必須。P1も拡張全体の受入には必要だが、P0の技術受入後に実案件で確認できる。IDを省略して拡張全体を完了扱いしない。各GAH-PRnnは同じ番号のGAH-PACnnで検証する。

### GAH-PR01 / P0: 実案件を再現できる接続契約

利用者が所有または利用許可を持つ開発repoと評価対象を、製品入口から登録・評価・比較・表示できること。接続manifestには対象revision/digest、適用Control、利用条件、取得範囲、ラベル来歴、adapter/評価器版、役割、資源profile、保持条件を含める。未対応入力を固定fixtureへ無言で置換しない。実装方式・新CLI名・Schemaは詳細仕様で決める。

**GAH-PAC01:** UC-CI 2repo（少なくとも1つは本製品以外）とUC-LLM 1評価対象を選び、各対象の登録からレポートまで追える。事前に、許可・前提・測定方式を基準管理AIが記録する。別revision、必須設定欠落、未対応形式、権限不足を明示拒否する。再現不能な外部model版は不明と表示し、固定版の比較受入へ数えない。対象未選定・許可未確認ならNOT_RUNのまま。

### GAH-PR02 / P1: UC-CIで実際の劣化を捉える

2repoの履歴から合計20組以上の変更前後を選び、各repoを5組以上含める。制約または検査に関係する変更を対象とし、単なる版番号変更で件数を満たさない。これとは別に正常な変更100件と、安全な固定変更による検査系の校正集合を用意する。実際の履歴と検査用変更を別集計にし、通常開発・本番を破壊しない隔離評価とする。

**GAH-PAC02:** 校正は既存の10 Control・5 Mutation familyの適用する全義務を覆い、期待判定との不一致0件。実履歴で独立に確定した適用範囲内の必須違反は全件Findingへ対応し、Critical見逃し0件。正常100件に対する誤った要対応通知は5件以下、誤ったCriticalは0件。不明ラベルを正常分母へ入れず、必要件数に不足すれば未受入。少なくとも1件の実履歴由来の劣化について原因・修復後再検証を結ぶ。得られない場合は実劣化への効果を未実証とする。repo別・Control別の適用範囲と非被覆も表示する。

### GAH-PR03 / P1: UC-LLMで実利用の変化を測る

利用許可と秘匿処理を確認した実利用由来の受入集合を、調整・開発・校正用集合から分離する。要検知200件以上・正常200件以上、各必須カテゴリで正負各100件以上を維持する。同一シナリオの派生・反復を独立件数へ増やさない。対象の2版または実在する2設定を同一集合で比較し、版以外の条件を固定する。実利用集合に対するbaselineは別に作り、合成集合の点数との差を性能変化と呼ばない。期待ラベルが割れた入力は不明に保ち、対象自身の回答をそのまま正解へ採用しない。

**GAH-PAC03:** 独立に固定した期待ラベルと測定器校正を用い、TP/FN/TN/FP、分母、欠損、カテゴリ別の差、遅延と使用資源が追える。集計を別の算術照合で再現し、正常タスク達成率も独立した期待結果で測る。欠測・二重配送・不明ラベル・評価器変更の対照例を正しく区別する。対象自身の低性能は有効な「劣化」結果になり得るため、拡張受入のために対象をHEALTHYへ誘導しない。本番分布への推定を主張する場合はR29の確かさを別途満たす。

### GAH-PR04 / P1: 保守負担の削減を実証する

既存の確認手順とGAH使用時で、同程度の変更について原因特定から判定・再確認までを比較する。管理AIの実作業時間、呼出数/token、計算資源、人間への介入依頼回数、誤警報の処理を記録する。人間が普段作業していない工程について「人件費削減」を捏造しない。

**GAH-PAC04:** 合計20件以上の対応観測を取り、両UCから各5件以上含める。順序・習熟・担当差を記録し、同じ正解と証拠水準で比較する。調査・再確認に要した実作業時間の中央値を既存手順比30%以上削減し、人間への介入依頼回数と総処理資源は増やさない。待ち時間を別掲する。目標に届かない、比較相手の既存手順がない、正解が不明な場合は効果未実証。観測期間は原則10営業日、最大20営業日で一度評価を閉じ、不足を隠して延々と継続しない。

### GAH-PR05 / P0: 性能の測定条件を固定する

単体処理、製品通常run、初回準備、CIを別に測定する。基準版は公開commit `c6a575ec0f00ec461a4757aeab62355645654433`、候補版は不変なsource snapshotを指定する。同一入力・期待結果・資源上限の比較と、追加機能による増分を分離する。

**GAH-PAC05:** 測定manifestと結果にOS/kernel、CPU/RAM、Docker/image、Python、storage、時計検査、並列度、同時負荷、DB/集合のdigest、cold/warm、計測区間を含める。wall time、CPU時間、全子処理を含むpeak RSS、read/write量、copy/serialize/hash/DB走査/authority呼出数、保存容量、失敗・再試行を測る。不可視の指標を0としない。計測自身の負荷も記録する。通常run・全件CIは基準/候補各3回を事前計画し、中央値と全観測の最大を報告する。開始後の失敗を都合よく捨てない。

### GAH-PR06 / P0: 同じ検査の通常実行を速くする

固定合成400ケース・2variantの通常800試行/1200段階を、評価範囲・資源制限・権限確認を維持して効率化する。対象モデルの応答時間とharnessの処理負荷を分ける。初回採択・比較を含む全工程の時間も別に報告する。

**GAH-PAC06:** §4の基準環境で、通常run開始要求からfreshなCI照会と必要な停止・回収・精算確認まで、中央値1800秒以下、最大2700秒以下、中央値は同条件基準版の60%以下。対象入力・配送・結果・分類・Findingの意味が一致し、予定の間引きと未精算0扱いは0件。CPU時間の合計を増やさず、cold startも上記の最大内。ID/時刻の違いを除外する場合は、比較前に許容フィールドを固定し、内容のdigest照合を外さない。劣化・取消し経路も既存の停止条件を維持する。

### GAH-PR07 / P0: 照会の処理量とキャッシュを制御する

候補・状態・レポートの照会が、履歴や証拠の増加で不要なdeep copy・全件再構築を繰り返さないこと。最適化のためのcacheは容量上限と無効化規則を持ち、現在の認証・撤回・世代照合を飛ばさない。

**GAH-PAC07:** 800試行の保存状態で、候補照会・現在CI・レポートをそれぞれ別計測し、100回のwarm照会のp95（昇順95番目）1秒以下、最大2秒以下、別プロセス初回3回の最大3秒以下。対象件数400/800/1600で、コピー・DB走査の処理要素数と直列化byte数を別々に計数し、各系列が倍増ごとに2.5倍以下。0を分母にした倍率は算出せず、新規発生として内訳を示す。履歴run数1/10/100の通常一覧は上限100件のpageに制限し、点照会が全履歴本文をコピーしないことを計数で確認する。失効・契約更新・対象変更・削除・移行・再起動を挟む対照試験で旧cacheによる成功0件。上限到達時は再計算または明示失敗とし、証拠を欠いた成功を返さない。

### GAH-PR08 / P0: CIの待ち時間と総費用を減らす

実測時間に基づいて全件CIを分割し、早期フィードバックと最終gateの適用範囲を表示する。全件discovery、重複・欠落・stale planの拒否、全必須jobの集約を維持する。共有setupを不要に分断せず、同一対象の重複起動を制御する。

**GAH-PAC08:** 同条件の各3回で、早期結果の中央値3分以下、全件gateの中央値30分以下・最大45分以下、総runner時間の中央値120分以下かつ基準版の60%以下。新規テスト込みの全件を絶対目標に含め、共通907件と追加分の費用も分ける。queue待ちを除く値とpushからの総時間を両方示す。skip/fail/cancel/未起動/別SHA/期限切れの必須jobがあれば全件成功にしない。早期subsetだけではCI成功権限を発行しない。旧run取消しはGitHub側の終了と製品内の停止・未精算を別に確認する。手動/週次runtimeの成功が、pushの未実行を埋めない。

### GAH-PR09 / P0: 初回利用を一つの手順で完了する

READMEから一つのquickstartへ進み、前提診断、設定生成、sample契約・baseline、初回評価、結果表示まで進めること。利用者が内部JSONを手で書いたり複数仕様書を往復したりする必要を減らす。sampleと実案件への切替点、管理AIと候補AIの役割を明示する。

**GAH-PAC09:** §4の両OS経路で、作成者の会話履歴を持たない新規contextの管理AIが各2回、計4回完了する。両OSでUC-CIとUC-LLMの手順を1回ずつ選んで検証する。前提ツール導入済みの新規workspaceから手入力コマンド5本以内、初回の製品sample評価・現在CI・結果表示まで30分以内。30分にはimage取得を含め、取得元・回線・cache条件を記録する。OS/Docker導入を含む総所要時間も別記する。秘密情報・有料API不要、追加説明・手動DB修正なし。sampleは選択したUCの採択済み範囲を全件評価し、diagnosticの終了を製品成功としない。既存環境・データを上書きせず、再実行で同じ設定や採択を二重作成しない。

### GAH-PR10 / P0: 開始前診断で環境不成立を説明する

開始前にPython/Docker/image、OS機能、identity、資源、保存領域、契約とbaseline、時計の前提を検査する。診断は原則読み取りで、clock観測等に一時資源が必要な場合は作成内容・上限・回収を明示する。環境を変更する修復は別操作とする。

**GAH-PAC10:** Docker停止、image不足、権限不一致、DB版違い、容量不足、資源上限不足、時計逆行/stepの各条件で、理由・影響範囲・具体的な復旧手順を返す。必須不成立のまま評価を開始しない。時計の許容値は既存契約を維持し、診断合格後の実行中異常も停止条件へ反映する。時刻同期停止、権限拡大、既存DB初期化・volume削除、証拠失効解除を診断に埋め込まない。未知・未対応OSは成功扱いしない。

### GAH-PR11 / P0: 判定の理由と次の作業を示す

JSONと人間向け要約に、対象revision、run、契約/baseline世代、計測と現在CIの時刻、判定理由、未評価・不明・未精算、根拠参照、次の操作を出す。終了codeと既存の意味は維持する。生成AIの補足説明は計算済み判定を書き換えない。

**GAH-PAC11:** HEALTHY、WARNING、既知違反、証拠不足、取消し、停止不明、未精算、撤回の各状態について両出力が同じ事実を示す。利用者が「何を評価したか・なぜこの判定か・次に何をするか」をrun参照から追える。対処方法は実装済みの操作へ結び、権限が必要なら役割を示す。最終確認を装った古い表示と、無害な診断の成功誤表示0件。理由code等の機械可読契約は詳細仕様と互換性検証に固定する。

### GAH-PR12 / P0: 中断・更新後も運用できる

取消し・再開・所有資源の回収、採択済み保持方針による容量管理、対応DBの明示移行・復旧を一つの運用手順にする。診断bundleは必要最小限のmetadataを既定にし、秘密値や生の利用入力を自動出力しない。

**GAH-PAC12:** 中断・再起動・遅延精算・容量不足・移行失敗を試し、元のrun/receipt・未解消予約が保持される。既知対応版の移行と失敗時復旧を確認し、未対応版は拒否する。rollbackは新形式を旧版へ無理に読ませず、復旧先の形式・書込停止区間を示す。cache上限は数値で設定・記録し、10回の同一運用で上限内。証拠容量はcacheと別に扱い、保持期限・未解消run・現在判定への依存を確認して処理する。所有外資源の削除0件、既定診断bundleへの秘密値・raw input混入0件。

### GAH-PR13 / P0: 最適化前後の判定を保持する

処理速度と導入性の改善によって判定・権限・予算・Evidenceの意味が変わらないことを独立照合する。性能試験の成功だけを品質の根拠にしない。

**GAH-PAC13:** 全件回帰と既存32条件への影響表を作り、変更経路の実接続で正常・違反・欠損・失効・取消し・資源不足を照合する。GAH-PR06の同条件比較に加え、変更対象外にも影響が及ぶ場合は受入を拡大する。差分のない重い全MVP検証を理由なく反復しない。故障例を性能集計から除外しても故障結果は別に残し、機能不合格があれば性能達成だけで受入しない。古いEvidenceのbyteやMVP受入記録を書き換えない。

### GAH-PR14 / P0: 管理AIの採択と拡張の進捗を追跡する

基準管理AIが対象・oracle・性能測定計画・許容範囲を開始前に版固定し、validatorが決定的に照合する。候補を作成するidentityに閾値・期待ラベル・結果の採択権限を渡さない。通常採択は既存方針の権限と上限の中で行う。

**GAH-PAC14:** 各PR/PACに対象source、計画版、結果、根拠、残る制約を記録する。状態はNOT_RUN/PASS/FAIL/INCONCLUSIVEを区別し、欠測はPASSにならない。実行後の閾値引下げ・母集団差替え・除外変更は新しい計画版と理由を必要とし、元の失敗を保持する。性能目標を満たすための既存制約緩和は通常の自動採択対象外。文書検収、技術受入、実案件での有用性確認、GitHub公開を別状態で表示する。

## 4. 測定環境・予算の提案

| 項目 | 拡張で固定する条件 |
|---|---|
| 性能基準環境 | Linux x86_64、専有4 vCPU・8 GiB RAM・SSD・Docker Linux Engine。OS/kernel/Python/imageとstorage条件はM0で実値を固定し公開可能なmanifestへ記録。GPU・実LLM待ちは固定fixtureの測定へ混ぜない |
| 導入受入の対象 | 上記LinuxとWindows 11 + WSL2 + Docker DesktopのLinux Engine。Windows経路も安定時計が前提。未対応構成は列挙し、両者の性能同等性は主張しない |
| 製品の制限 | full並列4、PR並列2、broker 0.5 CPU/128 MiBを維持。製品fullの時間上限5400秒とAPI・token・24時間予算は既存方針を維持。1800秒は追加性能目標で、新しい停止上限ではない |
| CI測定 | 最大12並列。runnerの実資源とイメージ、テスト集合、workflow版を記録。単一機4分割の履歴を独立runnerの改善baselineに代用しない |
| 反復 | 基準/候補各3回。coldを各1回、warmを各2回に固定。照会はPR07の回数を別適用。フル性能試験は一つの候補版につき原則この6回と機能故障の再現1回を上限とし、原因・修正のない追加反復をしない |
| 外部費用 | sample・性能fixtureは従量課金APIを使わない。pilotは採択済みPolicyProfile内とし、PR USD 2/full USD 10、直近24時間USD 20を上限として未知使用量と予約を合算。接続先利用許可を文書作成だけで付与しない |

性能測定の最初の1回をpilotとして途中観測し、件数・計時・資源制限・期待判定を確認してから残りを実行する。時計不成立や計測故障による無効観測は記録し、再計画する。成功した回だけの選択、除外理由の事後作成は行わない。3回の中央値/最大はその環境の受入値であり、母集団のp95を推定した値ではない。
