# 初回baselineから比較契約への移行詳細仕様

[採択・更新仕様](baseline-adoption-detail-spec.md)の初回後の接続を具体化する。
[要求](requirements.md)と[初回・採択契約](contracts/lifecycle-contract.md)を変更せず、
旧条件を固定したまま比較必須の契約を検証する。事前検査に続き、候補の保存・実行開始・
資源精算・Evidence保存に続き、generation 2への専用検証・採択を接続する。
通常回帰・通常CIは、候補実行や採択の成功だけでは成立しない。

## 1. 循環を避ける実行順序

1. 初回契約generation 1と、完了した初回candidateに基づくbaseline generation 1を採択する。
2. managerは別ID・generation 2の契約をproposalへ保存する。旧契約の方針、Registry、
   CaseSet、校正集合、evaluator、カテゴリ、必要出力を維持し、比較だけを
   `required`、採択済みbaselineの完全参照、`reason=null`、`changed_axes=[]`へ変更する。
3. validatorは保存済みのproposal、旧契約と履歴、baselineと全根拠を同じtransactionで
   検査する。ここで返すpreflightは候補実行の前提確認であり、採択validationではない。
4. proposalの版へ固定した候補専用runを作る。候補には旧条件での回帰と
   新条件の受入を実行し、別々の目的・binding・Evidence・closureを保存する。
   候補runを採択済み契約に基づく通常runやCI成功へ読み替えない。
5. 全根拠を再検査したvalidationを使い、managerが旧・新契約とbaselineの期待世代を
   同じ確定点で検査してから採択する。現行pointerと不変履歴の更新は同一transactionとする。

手順5の採択validation・原子的更新を実装し、[507テストと実Docker150項目](evidence/mvp-contract-adoption-20260912/README.md)で接続を確認した。
preflightや候補の作成receiptを、保存済み採択validationの代用品にしない。
契約の値を緩める改訂、baseline自体の更新、target等の条件差は別の更新検証を必要とし、
この限定した初回移行へ通さない。初回契約の比較非適用を通常回帰の免除に使わない。

## 2. 純粋な条件検査

`bind_contract_transition(previous_contract, next_contract, baseline_record=..., baseline_source_bound=...)`
は厳密な構造検査と実体からの参照再計算を行う。source bundleは既存runの8個のcore fieldを
持ち、再bindingした値と完全一致する必要がある。余剰fieldや入力の書換えを許さない。

旧契約とsource契約、baselineのsource run・TrialPlan・方針・Registry・CaseSet・target・
evaluator・oracle・反復条件を照合し、次契約のgenerationが1から2へ一つ進むこと、
別contract IDであること、比較以外の条件が変わらないことを確認する。
baselineと旧契約の完全参照はkind・ID・digestの全てで一致させる。

この関数にはDB、認証、時計を渡さない。返す構造検査結果からEvidenceの存在、期限、
採択、実行完了、現在利用を推測しない。`ci_eligible`、`authority_connected`、
`adoption_verified`は全てfalseである。

## 3. authorityの事前検査

`contract_preflight`はOS認証されたvalidatorだけが呼べる。要求は次の項目に限定する。

| 項目 | 内容 |
|---|---|
| schema_version / action / request_id | 1 / contract_preflight / 要求ID |
| proposal_id | managerが保存した次契約proposal |
| baseline_series_id | 現行baseline系列 |
| expected_contract_ref | 旧契約の完全参照 |
| expected_baseline_ref | 採択済みbaselineの完全参照 |

同一transactionで次を実行する。

- proposalの本文digestと列の世代・manager/contextを照合する。
- 契約currentと不変履歴が完全一致すること、旧契約のvalidation、方針・校正が現在も有効なことを確認する。
- baselineのcurrent・不変採択・proposal・validationを再検査し、Evidence、実入力、Decision、精算を確認する。
- baseline recordの`source_run_ref`から完了済み初回candidateの保存bundleを解決し、
  `baseline_source_bound`へ渡す。次契約proposalを`next_contract`、現行旧契約を
  `previous_contract`へ渡した`bind_contract_transition`の結果を`transition`へ含める。
  まだ存在しない移行候補runのEvidenceをpreflightの前提へ循環させない。

成功結果は`preflight_ready=true`、`candidate_run_required=true`、`adoption_verified=false`、
`ci_eligible=false`を返す。検査時刻とpermission generationはその照会時の値であり、
後続実行の許可証ではない。新しいvalidation、run、operation、adoptionを作らない。
AdoptionStoreの単調時計・認証の管理情報は通常どおり更新できる。

このactionはfresh照会であり、同一request IDでも撤回・期限・permissionと最新pointerを
再計算する。旧preflightの表示や終了コードを再利用して採択しない。
初回用`contract_validate`/`contract_adopt`はgeneration 2を拒否し、以下の専用APIで採択する。
後続の候補実行開始と採択の各適用時点では、LC02の権限・世代・現行方針・必要証拠・
最新失効状態を再照合する。preflightの成功を持参したことによって、この再検査を省略しない。

## 4. 候補の保存と実行

`contract_candidate_prepare`はvalidator専用で、preflightと同じ4つの前提fieldに
`candidate_id`、`old_run_id`、`new_run_id`を加える。schema_version、action、request_id以外の
余剰fieldを受け付けない。同じtransactionで現在前提を再検査し、固定factoryで生成した候補と
新旧run IDの予約を保存する。既存runや別候補のIDを再利用しない。

| side | purpose | 契約 | 実行計画 |
|---|---|---|---|
| old | contract_old_regression | 保存したgeneration 1、比較非適用 | 同じ条件を新たに15件実行 |
| new | contract_candidate | proposalのgeneration 2、比較必須 | baseline 15件とcandidate 15件の30件 |

両runはfull profileとする。元の固定15件packを検証し、入力・oracle・target・evaluator・
Registry・CaseSet・校正集合の完全参照を保持する。新しいpackや初回runの目的へ偽装せず、
検証済み入力からrun固有のplanとmaterializationを生成する。旧sourceの実測を、新たな旧条件
回帰の実行件数へ数えない。対象や閾値を変える更新はこのfactoryの対象外である。

`contract_candidate_begin`はoperator専用で、candidate_idとsideだけを受ける。保存時の
permission generationと現在のmanager/validator失効状態、旧契約・baselineの前提を再確認し、
resource runとeval runを同じtransactionで開始する。owner lease IDは開始request_idである。
開始済みsideを別request_idで重複作成しない。通常`run_begin`からの候補purposeや予約IDの
利用は拒否する。新旧runのdeadlineはprepare時に固定し、開始や再起動で延長しない。

予約、dispatch、Evidence開始の直前にも現在前提を再検査する。停止済みの観測・精算・
Evidence保存は保存版で照合し、撤回によって処理済み費用や観測を失わない。
候補の作成・開始・終了receiptの同一request再配送は不変履歴を返す。
この再配送は新たな実行許可ではなく、現在利用はfresh照会で検査する。

新旧は別のEvidence・Decision・closureを保存する。Evidenceのpurposeはnormalで、
観測から24時間の現行期限を適用する。初回baseline用30日へ延長しない。
候補の束縛先は採択後もproposalの保存版とし、通常CIのrunへ再解釈しない。
候補段階の`adoption_verified`と`ci_eligible`はfalseである。

## 5. 候補Evidenceの検証と採択

| action | 主体 | schema_version/action/request_id以外の要求field |
|---|---|---|
| contract_candidate_validate | validator | candidate_id、validation_id |
| contract_candidate_adopt | manager | candidate_id、validation_id、expected_contract_generation、expected_baseline_generation |

期待世代は整数の1とする。この移行はbaseline generation 1を保持し、契約だけを1から2へ進める。
validatorは現在の旧契約・baseline・初回sourceを再検査したうえで、新旧候補の完了した保存実体を
解決する。候補の保存bound、5 artifactの完全参照、終端Decision、Evidenceの期限・撤回・権限、
全attemptに対応する停止・精算、closureと当該runの資源残高の一致を確認する。
新旧ともHEALTHYまたはWARNINGを必要とし、入力の実体化と全資源の精算を満たす。
全runを合算する24時間費用は別runの予約や時間経過でも変化するため、過去closureとの
現在値の一致条件には含めない。保存closure自体の完全性はreceiptのdigestで検査する。

専用validationは既存`eval_validations`へ保存し、kindを`contract_transition_validation`とする。
candidate、proposal、旧契約、baseline、新旧receiptの完全参照、次契約全文、検査時刻、
permission generation、validator/contextを保持する。TTLは既存と同じ86,400秒であり、
その間でも採択時に全前提と証拠を再検査する。本文の比較では検査時刻だけを除く。

managerはvalidationと候補の一致を確認し、旧契約とbaselineの期待世代・完全参照が現在も
一致することを検査する。同じtransactionで契約currentをgenerationと旧digestによるCASで更新し、
不変のgeneration 2履歴を挿入する。片側の保存に失敗した場合、pointer、履歴、操作receiptを
まとめてrollbackする。成功応答は`adoption_verified=true`、`ci_eligible=false`である。

採択後の`contract_current`はgen2の履歴とvalidationから旧gen1履歴へ進み、旧校正・方針・
validation、baselineと初回source、新旧候補Evidenceを再検査する。旧gen1のcurrentへの復帰を
要求せず、保存世代から解決することで循環を避ける。根拠の期限・撤回・permission変更で
`valid=false`になるが、採択receiptや候補runのpurposeを書き換えない。
同一requestの採択再配送は不変receiptであり、現在の利用許可ではない。

通常gen2 runの比較context・入力の実体化は次工程とし、`run_begin`は
`BASELINE_CONTEXT_UNAVAILABLE`で明示拒否する。採択だけで全MVPやCI接続済みとしない。

## 6. 保存形式と移行

authority DB v4に`transition_candidates`と`transition_runs`を追加する。後者はrun IDを
主キーとし、candidate/sideも一意にする。新規DBと既知旧版からの明示移行で同じDDLを使う。
既存v3は実装拡張digest、bootstrap/validator設定、保存列、canonical payload/hashと対応する
保存参照を検査する。イメージ全体のsources_digestを実装拡張digestの代わりに使わない。
既知v2は従来の履歴作成処理を通してからv4表を追加する。版と設定digestは最後に更新し、
途中失敗は全てrollbackする。既存receiptを移行後の実行結果へ書き換えない。

専用採択は既存表を使用するため列形式はv4のままである。既知の候補run実装v4からの
明示upgradeでは、設定、canonical本文・hash、gen1履歴、候補のfactory再結合とrun対応を
確認し、extension digestだけを同一transactionで更新する。未知実装、列の不一致、
旧v4を装ったgen2採択DBを受け付けない。通常起動による自動更新は行わない。

## 7. 履歴と今後の受入

旧runの実行・Evidence解決は保存された契約世代から行う。現行実装の`_check_start`は
`eval_adoptions`をrunの保存世代で解決しているため、最新pointerへの読み替えは加えない。
実行継続には当時の条件の現在有効性を再検査し、停止済み観測の保存とは分ける。

今回の検証では採択validation、両期待世代のCAS、片側保存失敗時のrollback、再起動後の
gen2 currentと根拠撤回を確認した。更新後の通常run、条件変更を伴う契約・baseline更新と
通常CIの受入は、次の接続工程で確認する。
