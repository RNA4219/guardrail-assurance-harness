# 初回baselineから比較契約への移行詳細仕様

[採択・更新仕様](baseline-adoption-detail-spec.md)の初回後の接続を具体化する。
[要求](requirements.md)と[初回・採択契約](contracts/lifecycle-contract.md)を変更せず、
旧条件を固定したまま比較必須の契約を検証する。現在の実装対象は条件の事前検査であり、
generation 2の採択・通常回帰・通常CIは、この検査の成功では成立しない。

## 1. 循環を避ける実行順序

1. 初回契約generation 1と、完了した初回candidateに基づくbaseline generation 1を採択する。
2. managerは別ID・generation 2の契約をproposalへ保存する。旧契約の方針、Registry、
   CaseSet、校正集合、evaluator、カテゴリ、必要出力を維持し、比較だけを
   `required`、採択済みbaselineの完全参照、`reason=null`、`changed_axes=[]`へ変更する。
3. validatorは保存済みのproposal、旧契約と履歴、baselineと全根拠を同じtransactionで
   検査する。ここで返すpreflightは候補実行の前提確認であり、採択validationではない。
4. 次の接続工程で、proposalの版へ固定した候補専用runを作る。候補には旧条件での回帰と
   新条件の受入を実行し、別々の目的・binding・Evidence・closureを保存する。
   候補runを採択済み契約に基づく通常runやCI成功へ読み替えない。
5. 全根拠を再検査したvalidationを使い、managerが旧・新契約とbaselineの期待世代を
   同じ確定点で検査してから採択する。現行pointerと不変履歴の更新は同一transactionとする。

手順4〜5は未接続である。preflightを保存済みvalidationの代用品にしない。
契約の値を緩める改訂、baseline自体の更新、target等の条件差は別の更新検証を必要とし、
この限定した初回移行へ通さない。初回契約の比較非適用を通常回帰の免除に使わない。

## 2. 純粋な条件検査

`bind_contract_transition(previous_contract, next_contract, baseline_record=..., baseline_source_bound=...)`
は厳密な構造検査と実体からの参照再計算を行う。source bundleは既存runの8個のcore fieldを
持ち、再bindingした値と完全一致する必要がある。余剰fieldや入力の書換えを許さない。

旧契約とsource契約、baselineのsource run・TrialPlan・方針・Registry・CaseSet・target・
evaluator・oracle・反復条件を照合し、次契約のgenerationが1から2へ一つ進むこと、
別contract IDであること、比較以外の条件が変わらないことを確認する。
baselineと旧契約の完全参照はkind・ID・digestの全てで一致させる。

この関数にはDB、認証、時計を渡さない。返す構造検査結果からEvidenceの存在、期限、
採択、実行完了、現在利用を推測しない。`ci_eligible`、`authority_connected`、
`adoption_verified`は全てfalseである。

## 3. authorityの事前検査

`contract_preflight`はOS認証されたvalidatorだけが呼べる。要求は次の項目に限定する。

| 項目 | 内容 |
|---|---|
| schema_version / action / request_id | 1 / contract_preflight / 要求ID |
| proposal_id | managerが保存した次契約proposal |
| baseline_series_id | 現行baseline系列 |
| expected_contract_ref | 旧契約の完全参照 |
| expected_baseline_ref | 採択済みbaselineの完全参照 |

同一transactionで次を実行する。

- proposalの本文digestと列の世代・manager/contextを照合する。
- 契約currentと不変履歴が完全一致すること、旧契約のvalidation、方針・校正が現在も有効なことを確認する。
- baselineのcurrent・不変採択・proposal・validationを再検査し、Evidence、実入力、Decision、精算を確認する。
- 保存sourceを解決して純粋な条件検査を行う。

成功結果は`preflight_ready=true`、`candidate_run_required=true`、`adoption_verified=false`、
`ci_eligible=false`を返す。検査時刻とpermission generationはその照会時の値であり、
後続実行の許可証ではない。新しいvalidation、run、operation、adoptionを作らない。
AdoptionStoreの単調時計・認証の管理情報は通常どおり更新できる。

このactionはfresh照会であり、同一request IDでも撤回・期限・permissionと最新pointerを
再計算する。旧preflightの表示や終了コードを再利用して採択しない。
現行`contract_validate`/`contract_adopt`は候補run未接続のgeneration 2を拒否し続ける。

## 4. 履歴と今後の受入

旧runの実行・Evidence解決は保存された契約世代から行う。現行実装の`_check_start`は
`eval_adoptions`をrunの保存世代で解決しているため、最新pointerへの読み替えは加えない。
実行継続には当時の条件の現在有効性を再検査し、停止済み観測の保存とは分ける。

現在の受入対象は、初回移行の構造・現在前提・主体分離・再照会時の撤回・不変履歴の
保持までである。候補runの実行、両世代のCAS、旧条件回帰の実測、更新後の新旧run、
契約とbaselineの片側保存障害を含むrollbackは、接続後に別の実行証跡で確認する。

# 初回・採択・再開・終了の契約 v0.3

[評価契約](evaluation-contract.md)の補足。製品実装・正式Schemaではない。[見直し](../reviews/state-review-20260911.md)のSR01〜SR06に対応する。要求・初期方針を変更せず、重なった条件の適用順と信頼起点を定める。例は[状態例JSON](state-examples.v3.json)、製品試験は全件NOT_RUN。

## LC01: 初回の信頼起点

採択契約が存在しない初回は、信頼するGAH配布物の版に結ばれた不変のBootstrapContractを使用する。初期方針、固定受入検査、許可目的、必要出力、データ境界、予算profileを含め、管理AIやcandidateが自分の提案で置き換えない。内容digestだけを配布主体の認証とみなさず、配布物の認証・配置保護は実装時の前提として確認する。

BootstrapContractの許可目的は初期校正・契約の初回採択検証・初回baseline候補作成に限る。これらは全対象/管理profileを消費し、通常回帰CIの成功には使用しない。RunManifestは契約の種類と配布版を固定する。比較は明示的な非適用理由を必要とし、絶対条件・データ用途・必要証拠・成果物・校正を省略しない。初期校正自身は固定された既知ラベルと決定的な受入検査で評価し、まだ校正していない評価器の自己採点を合格根拠にしない。

初回採択では現行世代なしを明示し、固定受入検査で初回契約を検証してLC02で採択する。baseline未採択なら、採択済み初回契約の候補作成目的で評価してbaselineを採択する。baseline参照を更新する場合も新しい契約版と世代を作る。前提が未充足の契約は回帰目的に使用できない。採択済み契約が存在する状態で、その拒否・失効を回避するために初回へ戻らない。移行・復旧は別の明示的な手順を必要とする。

必要な配布契約・固定検査・校正データがなければ入力拒否/HOLD/2とする。文書上のBootstrapContractの追加はそれらの実装完了を意味しない。

## LC02: 採択の確定時検査

AdoptionRecordはproposal_digest、検査時刻、検査した権限/方針/失効世代も保持する。検証を終えた時点と採択の適用時点を分け、適用の一つの原子的な確定点で次の条件が全て成立することを要求する。

- 認証済みの呼出主体とcontextに、現在も当該対象・操作への権限がある。
- expected_generationと現行世代が一致し、検査した提案内容が同じである。
- 現行の許可方針・初期値の境界に適合し、必要な旧条件評価と新条件の受入証拠が揃う。
- 必要証拠が確定時刻で有効であり、参照する最新の失効状態と校正状態を取得できる。

検査と可変参照の更新との間に、これらの世代が変われば再検査する。その整合した確定点を実装方式で保証できなければ採択しない。期限切れ・失効・権限取消し・不明・世代競合では現在の採択参照を維持し、可能な範囲で拒否理由を記録する。保存障害時も採択成功を返さない。

同じ要求ID・内容の再配送は、認証・閲覧権限を確認して過去の採択receiptを返すだけとする。失効した採択や権限を復活させず、新規の有効性保証にもしない。現在の利用可否は別途照合する。内容が異なる再配送は拒否する。

## LC03: 所有世代と再開

RunLeaseはrun_id、owner_ref、単調増加するowner_epoch、所有期限を保持する論理契約。引継ぎは原子的に新しい所有世代を発行する。予約・dispatch・結果の採用・最終確定には現在の所有世代を要求する。古い世代の主体は新しい処理を始めず、正規結果やterminal receiptを書き換えない。leaseの実装製品・期限値は実装準備で決める。

操作ごとに不変のoperation_idを付け、予算予約とdispatch意図を送信前に永続化する。再開時に「未送信」と証明できる操作だけを開始できる。送信済み/未送信が不明な操作はUNKNOWNのまま予約を保持し、同じ内容を新しいIDで再送しない。元の終了・実行障害・副作用の状態を確認した後だけ、既存の再試行条件を適用する。外部処理のexactly-once実行を保証したとはみなさない。

旧主体から届いた内容は受信境界を通した監査材料にし、現主体がbinding・元操作・終了状態と整合を確認するまで正規結果として採用しない。単に古い世代という理由で費用・禁止違反・矛盾を消さない。認証した監督/課金イベントを同じoperation_idへ照合して、一度だけ精算する。終了・非課金/精算が未確認の予約は世代変更で解放しない。旧主体の外部処理の停止確認が取れなければ成功を確定しない。

runの元のdeadlineは変えない。再起動をまたぐ経過時間には停止期間を含め、保存した経過秒に新プロセスの稼働秒だけを足す方式を禁止する。信頼できる時刻の継続根拠から経過時間の保守的な上限を復元し、予算・予約・所有世代と合わせて確認する。時計の巻戻り、根拠不足などで復元できなければ再開して成功にしない。deadlineと同時刻では新規操作を開始しない。

## LC04: 費用の精度と精算

予算比較の単位は引き続きUSD百万分の一の整数とする。単価・確定請求額は信頼できる元の十進数/分数と出典・計算版を保存し、浮動小数点の表示丸めを判定に使用しない。より細かい正の金額は、操作ごとの総額を百万分の一単位へ**切り上げ**て会計用上界とする。切捨て・最近接丸めで正の費用を0にしない。実請求額と保守的な会計用上界は別fieldにする。

開始前は操作の最大請求額を同じ方法で切り上げて予約し、精算後は確定した操作総額の切上げ値でその予約を置換する。精算は一operation_idにつき一度。同一精算の再配送は増額せず、異なる精算額の再配送は矛盾としてHOLDにし、確認が終わるまで解放しない。分割通知なら総額確定前は予約を保持し、断片の切捨て合計で精算しない。0は非課金の根拠がある場合に限る。

例: 0.4百万分の一USDは会計上1、2は2、2.01は3。上界を足すため、細かな課金が多い場合は実請求額より早く既存予算に達し得る。これは保守的な計上であり予算額の変更ではない。料金/最大額の根拠が不明なら開始不可、開始後の料金不明は既存のbudget_closure規則に従う。

## LC05: 保存・入力・送信の前のデータ境界

未信頼の入力・出力は、永続化または別の処理へ渡す前に、採択済みのデータ方針に照合する。対象はraw artifactだけでなく、stdout/stderr収集、telemetry、debug、一時ファイル、計画本文、モデルprompt、外部転送を含む。payload内の「合成」「安全」という自己申告は許可根拠にしない。信頼した由来・許可した合成データ/形式・送信先・用途を確認し、変換/編集した出力も送出前に再検査する。

判定は容量を限定した検査領域で行い、判定前に無制限にbufferしたり、通常ログへ流したりしない。未知・拒否・検査器障害の場合、そのpayloadを保存/送信/モデル入力に使わない。理由code、run/operation参照、判定した方針版など、許可した最小限のmetadataだけを残す。拒否された文字列、その抜粋、低エントロピー値を推測できるdigestを既定で証跡に含めない。

許可範囲で定義した合成の負例は、明示した検査先にのみ渡せる。GAHが受入不能としたデータは、対象ガードレールの正常な拒否観測へ読み替えない。AttemptRecordのraw_artifact_refはこの場合明示的な欠落にし、data_dispositionと理由を記録する。拒否/不明により必須処理を完了できなければFAILED/2、入力境界不成立はHOLD、検査不能のみなら既存の必須不足の優先規則を適用する。存在しないraw証拠や新規観測を補わず成功を返さない。

受信前に外部providerが保持したデータの消去や、ホスト管理者からの完全保護を保証する契約ではない。runner/adapterの収集経路とモデル送信経路で実装し、payloadを含まない監査とともに検証する。

## LC06: 終了状態が重なる場合

取消し受付とterminal確定を同じrunの順序付きイベントとして直列化する。確定前に取消しを受け付けたら、停止確認待ちでも成功確定へ進まない。terminal確定後の取消しはalready_terminalとして別記録にし、確定済みreceiptを変更しない。

終了の優先順は次のとおり。Assuranceの既存の優先順とは別に判定する。

| 順 | 条件 | execution_status / 終了コード |
|---|---|---|
| 1 | 必須保存・出力・実行等の障害により有効なterminal記録/処理完了が成立しない | FAILED / 2 |
| 2 | 確定前に取消し受付済み、全子処理の停止確認済み、取消し記録の保存と出力が完了 | CANCELLED / 3 |
| 3 | 取消し受付済みで停止未確認 | 期限内は停止待ち。期限到達または確認不能でFAILED / 2 |
| 4 | 取消しなしで処理完了 | COMPLETED。Assurance・binding・出力・有効性に従い0または1 |

Critical違反と取消しが重なってもHOLDを保持する。さらに必要出力の保存が失敗したらHOLD/FAILED/2、保存でき停止確認済みならHOLD/CANCELLED/3。非Criticalの既知違反や不足理由も消さない。保存障害時の失敗通知は可能な出力先への最善努力であり、完全なreceiptが保存されたと捏造しない。取消し時にも料金不明の予約は保持するが、停止と取消し記録が完了していれば3を返せる。budget_closureは成功の必要条件であり取消しの課金免除ではない。
