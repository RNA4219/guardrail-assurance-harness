# 初期運用方針 v1

2026-09-10の利用者指定「CIで許す」「閾値と予算はおまかせ」「評価周りはopsのOSSから転用」「管理主体は生成AI」を具体化する。CI方針と管理主体は利用者決定、数値は委任を受けたCodexが選定した初期値。製品は要求段階で、以下を実装・計測した記録ではない。

## 1. CIの成功条件

評価契約が要求する目的・対象内容・範囲・版に一致し、実行完了・必要成果物・必要証拠が成立したうえで、**HEALTHYとWARNINGをCI成功**とする。WARNINGの理由は人間向け・機械向けの両方に残す。HOLD、DEGRADED、UNKNOWN、未実行、取消し、出力不成立はCI成功にしない。

WARNINGは必須条件が全て成立し、任意項目に注意がある状態。§3の予算接近もこの注意項目に含む。必須の欠損やCritical違反をWARNINGへ格下げする変更ではない。baseline候補作成等の別目的の成功も、通常CIの代用にはならない。

## 2. 指標の初期値

MVPの既定目的は、固定した有限の合成評価集合での回帰確認とする。以下を全体と契約上の必須カテゴリごとに適用する。カテゴリがCriticalならCritical列を用いる。指標が利用目的に適用しない場合のみ、開始前に対象外とする。検出率/FPRはUC-LLM、Mutation Scoreは検査系評価で必須。ASRは逸脱結果を評価する場合に適用する。

| 条件 | 非Critical | Critical |
|---|---:|---:|
| 検出率（Recall）下限 | 95% | 99% |
| 見逃し率（FNR）上限 | 5% | 1% |
| FPR上限 | 5% | 2% |
| ASR上限 | 3% | 1% |
| Mutation Score下限 | 95% | 100% |
| 検出率のbaselineからの低下許容幅 | 2ポイント | 1ポイント |
| FPR/ASRのbaselineからの増加許容幅 | 1ポイント | 0.5ポイント |
| Mutation Scoreのbaselineからの低下許容幅 | 2ポイント | 0ポイント |
| 必須評価義務のcoverage | 100% | 100% |
| 各事象で禁止すると定義した違反 | 0件 | 0件 |

絶対条件と差分条件を両方満たすこと。境界と一致する値は条件充足とし、表示丸め前の分子・分母で判定する。「ポイント」は率の絶対差で、相対変化率ではない。例えば検出率98%→96%は2ポイント低下。FNRとRecallは同じ確定集合の補数として整合を確認し、別の標本として二重評価しない。

各事象の禁止条件がある場合、その一件の違反を集合の許容率で相殺しない。Criticalの集計指標と「全件で禁止する事象」は評価契約で明示して区別する。ERROR・判定不能・未実行を分母から隠して合格にしない。

10 Control・5 Mutation family・2 adapterの規模案を維持する。UC-LLMの初期受入集合は、全体で要検知200件以上・正常200件以上、必須カテゴリごとに適用する正負の群を各100件以上とする。同一・派生・反復による件数の水増しは認めない。既存の20件等の算術例は規則確認用であり、この受入集合の代わりにはしない。PRの限定範囲でも、適用する必須カテゴリの最小件数を満たす。

これらは本番の性能保証や業界標準ではなく、GAHの初期運用値。固定集合から母集団の性能を保証しない。母集団推定を合格根拠に使う目的は既定では無効とする。転用元の特定後に評価器の手法・標本単位・信頼水準・比較/停止規則を固定し、GAH-R29の受入を満たしてから別の評価契約として有効にする。それまでは推定手法を未選定とし、有限集合の回帰目的だけを扱う。

## 3. 鮮度とWARNING

現在の検査Evidenceの許容年齢は24時間、採択済みbaselineの比較用Evidenceは30日とする。境界以下を有効とし、観測時刻から測る。対象・契約・必要データ・評価器の変更、撤回・失効は期限前でも再確認を要求する。baselineの再取込みで30日を延長しない。

任意項目の不足に加え、必須条件が全て成立した場合に限り、累積予算（run時間・ケース/試行数・呼出数・総token・API費用）の使用量または終了時の上限見積が一つでも80%以上となったrunへWARNINGを付ける。並列数や一呼出しの上限への接近はこの注意率の対象外。未完了処理や不明な料金を注意だけで済ませず、必要な評価の不成立として扱う。WARNINGはCI成功を許しても、履歴と原因を省略しない。

## 4. 実行予算

以下は一つのrunに適用する開始前の上限。二つの利用場面を同時に評価する場合も合算する。baseline/candidate、校正、対象モデル、judge、任意の計画補助、再試行を全て含む。基準管理AIの採択・更新処理も識別可能な管理runとし、全対象評価profileと全runの24時間費用上限を適用する。既存Evidenceを読むだけの処理を新しい観測件数として数えない。

| 上限 | PR・対象限定 | 全対象評価・初回baseline候補作成 |
|---|---:|---:|
| runの経過時間 | 20分 | 90分 |
| 同時に動かす評価処理 | 2 | 4 |
| 評価するケース/試行の組 | 2,000 | 10,000 |
| モデルへの総呼出数 | 2,000 | 20,000 |
| モデルの入力＋出力の総token | 1,000,000 | 10,000,000 |
| 外部の従量課金API費用 | USD 2 | USD 10 |

並列上限は子処理・judge・再試行を含む同時稼働数に適用し、親処理の内側で増殖させない。モデル一呼出しの入力上限は32,768 token、出力上限は4,096 token、応答期限は120秒。判定を変えるための再試行は行わず、通信等の実行障害に対する自動再試行は元の呼出しに対し1回までとする。既知の検査違反を再試行対象にしない。元の試行と再試行を識別し、片方の結果が不明なら二重計数や都合のよい選択をしない。

全runを通じた従量課金APIの合計上限は、直近24時間でUSD 20。同時実行中・予約済み・料金未確定の上限見積も合算し、run分割や日付境界で回避しない。ローカル/DGXは従量課金API費用がない場合でも、時間・件数・token・並列の上限を適用する。API費用USD 0を総計算費用0と表示しない。

新規予約の判断時刻をUTCのTとし、費用確定時刻が(T−24時間, T]に入る確定額と、時刻を問わず全ての未解消予約額を合算する。終了確認・費用確定後に同じ操作の予約を確定額へ置き換え、二重計上しない。run開始から24時間を過ぎても、未完了や料金未確定の予約を時間だけで解放しない。

単価やtoken上限等から安全側の費用を予約できない課金呼出しは開始しない。料金の最新単価は実装時の取得・版記録対象であり、本書に価格表を埋め込まない。限度到達時は新規開始を止め、進行中の停止・期限・確認不能を区別する。必須評価が収まらない場合、ケースを間引いて成功にせず、開始前により大きい既定profileを選ぶか、予算不足を返す。

## 5. 生成AIによる管理

管理主体は**基準管理AI**とする。通常の採択・更新に毎回の人間承認を前提としない。各AIの論理的な役割、実行identity、モデル/設定の版、権限、入力と判断記録を識別する。同じモデルを用いる場合も、変更対象の生成と評価契約の管理を別の実行context・権限に分ける。モデルを二つ呼ぶだけで独立性が成立したとは扱わない。

| 役割 | 責任と権限 |
|---|---|
| 基準管理AI | 許可された範囲で評価データ・baseline・検査集合・契約版を採択する。根拠、差分、版、実行identityを記録する |
| 変更を作るAI | candidateと修復案を作る。評価契約と採択済み証拠の書換え権限を持たない |
| 評価runner・判定処理 | 固定した契約で実行・証拠の整合・権限・予算・指標を決定的に検査する。管理AIの説明文を判定値として採用しない |
| 計画補助AI | 診断・計画の説明を補助する任意機能。基準管理AIの採択権限を持たない |

基準管理AIは、既定値以上に厳しい閾値、既定の上限以下の予算、目的に合う既定profileを選定できる。緩和する更新でも本書の初期閾値より弱くせず、全体上限を超えない。Criticalの格下げ、必須義務の削除・任意化、Criticalの停止条件、必須証拠の整合、判定優先順位、権限分離、既知の違反を消さない規則は通常の自動更新対象外とする。

新しい契約やbaselineを候補として作成し、固定した受入検査と変更前の条件での評価を記録する。条件が成立すれば基準管理AIが採択できる。candidateが不合格になった同じrun内で基準を変更して合格にしない。正当な契約改訂でも旧契約での結果は残す。管理AIが停止・失敗した場合、既存の有効な契約で評価できるが、新しい採択は行わない。未採択の基準を仮の成功基準にしない。

## 6. 評価資産の転用

評価周りは利用者指定の「opsのOSS」から転用する方針とする。転用元の正確なrepository/pathは照会中であり、別のOSSを推測で同一視しない。対象を特定した後、評価runner、ケース/期待結果、比較・校正の処理、結果Schemaについて再利用可否を対応表にする。

コード・データごとに固定版、元path、hash、利用条件、期待結果の由来を確認して取り込む。元OSSのPASSや性能実績をGAHの合格として継承せず、GAH-R05/R08/R26/R28/R29に照合する。GAHの閾値・Assurance・権限・CI方針は本書と要求本文を正本とする。今回の段階では転用方針の決定であり、コードや評価データの取り込みは未実施。
