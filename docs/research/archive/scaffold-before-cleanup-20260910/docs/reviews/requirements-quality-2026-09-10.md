# 要件定義v0.3の品質評価

## 1. 総合判定

**仕様化の基礎としては良好。利用者・要求単位・実現性の確認を条件に、仕様化へ進める。全面的な実装契約としての凍結は保留。**

目的、対象外、根拠の扱い、例外、機密境界、再現性、評価方法は具体的で、技術的な要求の網羅性が高い。一方、最初に誰のどの仕事を改善するのか、個々の義務をどの受入試験で判定するのか、広いM0をどの順序・資源で成立させるかは、追加の具体化が必要である。

これは文書の品質・準備状態の評価であり、製品の精度・安全性・性能の判定ではない。「問題がないことの証明」や利用者による全面承認を意味しない。静的な文書評価を100点満点の実測値へ見せないため、総合点や達成率には換算しない。

## 2. 対象と評価方法

- 対象: [要件定義](../requirements.md) v0.3、2,558行。
- SHA-256: `a2cbe58ffffbe458eed5888c075076b7fdab1528f95d62313de6ab289ccf448a`。
- 実施者: Codex。直前の改訂にも関与した同一評価者による自己評価で、独立した第三者レビューではない。
- 方法: 目的から出力・制約・受入条件までの読解、未決定事項の分類、IDと受入表の機械突合。
- 既存証跡: [敵対的レビュー](requirements-adversarial-2026-09-10.md) を利用。反例モデルの成功を今回の文書品質や製品品質の得点には流用しない。
- 範囲外: 市場調査の再検証、外部資料の更新確認、利用者インタビュー、工数見積り、製品実機試験。

「良好」は文書上の基礎が揃っていること、「要整理・補強」は判断の再現性を高める具体化が必要なこと、「未実証」は実験・利用者確認の証拠がまだないことを表す。特定の規格への適合認証ではない。

## 4. 優先して改善する5点

### QE-01: M0の主要利用者と主要作業を固定する

**分類: 要件の妥当性に関わる不足。仕様ベースライン凍結前に補強。**

「人間が理解する」だけでは、引継ぎ、既存保守、変更影響の確認など、何を最初に最適化するかを決めにくい。現在のUX評価は理解の正確さを測れる一方、評価参加者が実際の利用者を代表する条件と、既存の調査手順に対する効果の判定は明確でない。

追加する情報は、主要利用者の役割、利用前の知識・権限、最初の3つ程度の作業、入力する資料、必要な回答、作業の終了条件。Evidence到達時間を記録するだけでなく、時間を成功基準に使うか、正確さを優先するかも決める。

保守担当者等をここで利用者の決定事項として代入してはいない。実際の利用者・依頼者の確認が必要である。未確認であることと、製品価値がないことは別である。

### QE-02: 大きな契約を独立して判定できる義務に分ける

**分類: 明確さ・追跡可能性の不足。仕様記述の初期段階で対応。**

RUN-03には、completion policyの事前固定、空入力の状態、optional LLMの扱い、安全上の失敗、gold指標の流用禁止、終了後のpolicy変更禁止がまとまっている。受入表の1行だけでは、どこまで満たしたかを管理しにくい。

親IDを維持しながら枝番等で分け、それぞれに条件・期待結果・失敗時の状態・検証方法を対応付ける。新しい機能を増やす作業ではなく、既存の義務を検査単位へ整理する作業とする。少なくとも正常、空入力、全件未対応、必須stage失敗、取消、参照不整合は独立判定する。

**28/28の受入行対応はID単位の会計であり、全義務のテスト網羅100%ではない。**

### QE-03: M0を価値実証と公開受入の段階へ分けて進める

**分類: 実現性・計画の未実証。全面実装の見積り・確約前に確認。**

M0はTypeScript/JavaScript、React/Expressに加え、JSON/YAML、SQL、OpenAPI、Terraform、HTML/Markdown/Gitのsubset、cross-repo linking、機密制御、永続化、3ペインUIを含む。「最小vertical sliceが成立すること」と「M0の全受入に合格すること」は同じではない。

提案する順序は、契約と小さな合成fixture、指定版・指定経路の縦断解析、残るM0能力と障害制御、独立gold/性能/UXによる公開受入。各段階の対象、成果物、必要な人・環境、終了条件を決めてから見積もる。

これは実装順序の提案であり、既存M0要件を削除したりM1へ移した決定ではない。根拠・scope・機密境界を、後から付ける機能として外さない。

### QE-04: 評価の定義と、評価できる状態を分けて管理する

**分類: 検証準備。対応capabilityの受入前に解消。**

精度98%等の数値、少なくとも5系統・50 Behavior・capabilityごと200項目以上というcorpus条件、2名によるgold確認は、判定方法として具体的である。実装前だから未達なのは当然であり、それ自体を要件の欠陥とはしない。

ただし、それらを測る入力manifest、予測とgoldの照合rule、除外基準、正常/異常fixture、独立評価者、実行環境を準備しなければ、受入基準は運用できない。閾値の達成可能性もまだ判断できない。未実証を理由なく達成不能と断定せず、逆に目標を書いたことを実現性の証拠にしない。

評価準備の完了条件は、同じ予測・gold・ruleで同じTP/FP/FNになり、重複・scope違い・oracle混入を拒否できること。文書lintや有限反例モデルの成功は代替にならない。

### QE-05: 規範要件と研究・設計候補の保守単位を整理する

**分類: 変更管理・可読性。仕様化と同時に整理。**

現在の文書は規範要件、OSS比較、概念Schema、UI例、confidence式、実装候補、探索的な工程図を一つに含む。冒頭で規範と仮説を区別している点は適切だが、更新時に本文・最終ベースライン・表・図がずれる危険は残る。行数だけを理由に品質を下げているわけではない。

規範要件を正本として保ち、調査来歴、設計案、具体的な外部挙動、試験条件へリンクで接続する。仕様化時には、各項目が必須条件、設計候補、未決定、測定目標のどれかを追跡できるようにする。機械可読Schemaを作るときも、概念図の見た目だけでmandatory/nullableやhash対象を決めない。

## 5. 正常な設計保留と、先送りできない判断

| 項目 | 評価上の扱い | 決定すべき時点 |
|---|---|---|
| Graph保存方式、UI framework、parser/compilerの実装選択 | 要件段階で未選定でも正常。要件で特定技術を不必要に固定しない | 該当部分の設計・実装前 |
| 形式Schema、導出rule、completion policy、資源上限の既定値 | 要件が不足を認めている設計gate。仕様化で具体化できる | parser/Store/CLIの契約固定前 |
| 主要利用者と主要作業 | 要件の妥当性を左右するため技術選定だけでは解消しない | 仕様ベースライン凍結前 |
| 独立gold、評価者、性能・UX計測 | 受入準備。準備方法はあるが実施証拠が必要 | capability対応宣言・M0公開前 |
| 本体license・配布物の確認 | 公開前gateとして既に明記。今回の文書評価で決定しない | 外部公開前 |
| cloud provider・共有サーバ | M0では必須ではない。既定OFFの境界を維持 | 当該機能の有効化前 |

未決定事項に解決時点があることは文書の長所である。すべてを今すぐ決める必要はないが、「後で決める」から対応済みへ移すには決定と検証の記録が必要となる。
