# Guardrail Assurance Harness — 要求明確化案 v0.3

GAHは、登録されたガードレールとその検査系について、現在の証拠が有効か、以前より検知能力が落ちていないかを確認し、問題の根拠と修復計画を人間へ返す。

現在は要求段階。本書は利用者の要求明確化依頼に基づく**要求案**であり、製品の実装仕様・実測結果・全面承認ではない。原稿から継承した内容と今回補った判断規則は[対応表](requirements-traceability.md)で区別する。元の長文原稿・構成図・技術候補は[資料来歴](research/README.md)から参照する。

## 1. 誰の、何を解決するか

初期対象は次の二つ。2026-09-10の利用者の補足により、両方をMVPの対象とすることを確認した（GAH-D01）。v0.1の「coding agentの開発・CIを想定する」という仮定A01を置き換える。この確認は利用目的と対象範囲についてのもので、以下の要求案・運用閾値の全面承認を意味しない。

| 利用場面 | 利用者 | 解決する問題 |
|---|---|---|
| UC-CI: coding agentの開発・CI | agent開発者、CI管理者 | 変更によって制約が守られなくなったこと、またはその逸脱を検査系が検知できなくなったことを見つける |
| UC-LLM: LLMガードレール評価 | ガードレール開発者、評価担当者 | モデル・プロンプト・ガードレール設定等の変更に伴う、検出率・見逃し率・誤検知率の変化を追う |

担当者が知りたいのは、①どの制約を検査したか、②ガードレールや検査系に劣化があるか、③どこが未検証か、④修復後に何を再確認すべきか、の4点である。全エージェントの行動を人間が逐一読まなくても、対象範囲と根拠を辿れる状態にする。

GAHの判定は、宣言した対象・条件・時点の検証結果である。エージェント全体の絶対安全、未知の挙動の安全、法令適合、実行中の本番環境の保護を保証しない。

| 役割 | 責任 |
|---|---|
| Control owner | 守る条件、必要な検査、対象範囲、基準値・閾値の設定を管理する |
| CI/評価運用担当 | 入力と実行条件を固定し、検査結果・実行失敗・未検証を確認する |
| 修復担当 | Findingと計画を確認し、別の変更作業で修復と再検証を行う |
| GAH | 証拠を収集・検証し、決定的な判定と説明を出す。ownerのリスク受容判断を代行しない |

## 2. MVPの完成形と範囲

MVPでは、二つの利用場面それぞれで「Controlと評価目的を登録する → 隔離環境で固定ケースを評価する → 現在値と比較可能な基準との差を判定する → 根拠付きのFindingと修復計画を読む」という一連の流れを成立させる。

| 評価の種類 | 固定する主な入力 | 必要な確認 |
|---|---|---|
| UC-CI | 制約、変更前fixture、定義済みMutation、対応する検査系 | 通常時の制約遵守と、意図したfixtureの変化に対する検査系の反応を別々に評価し、前版との差を追う |
| UC-LLM | 要検知/正常の期待ラベル付き合成ケース、対象ガードレール、観測を判定する規則 | 検出率・見逃し率・誤検知率と件数を測定し、同じ評価条件で前版との差を追う |

証拠管理・比較・判定・Finding・計画・CI返却は共通要求とする。runは一方だけ、または両方を対象にできるが、対象と必須指標・評価義務を開始前に固定する。UC-LLMの性能測定だけのrunにMutation実行を一律には要求しない。対象外としたMutationについて検査系の有効性を主張せず、必要なMutation評価を実行後に除外しない。MVPの製品受入では両方の最小シナリオを確認する。

| 範囲 | MVPで要求する成果 |
|---|---|
| Control Registry | 守る条件・責任者・検査・証拠・判定条件の対応 |
| Mutation CI | 合成fixture内の定義済み変化に、検査系が反応したかの記録 |
| Decay Detection | 現在の評価、比較可能なbaselineとの差、証拠の鮮度と欠損の判定 |
| Remediation Planner | 原因候補、修正対象、再検証、将来の展開・復旧に必要な情報を含む計画 |
| 上記を支える必須機能 | 入力検証、adapter結果の正規化、指標、証拠の識別・保存、権限境界、予算、CI向け結果 |

本番への変更、実際のIAM/Policyの改変、公開先への書込み、運用中サービスの停止はMVPの処理に含めない。任意の対象を探索して攻撃を生成・実行する機能もMVPに含めない。generic command等の接続方式でも、この範囲を拡張しない。

署名・外部の改竄耐性ストレージ、専用IAM/OPA等のadapter拡充、運用対象のShadow/Canary/Promote/Rollback、全社的な権限管理・影響範囲予測、週次GC、Web UI、OSCAL連携は後期の検討事項。外部参照元の共通core抽出は再利用案であり、抽出完了をMVP着手の前提にはしない。

## 3. 用語と混同しない判定

| 用語 | 本書での意味 |
|---|---|
| Control | 守る条件と、その条件を確認する検査・証拠・判定方針の組 |
| ガードレール | 実際に操作や出力を制約する仕組み。GAH自体と区別する |
| 検査系 | ガードレールや対象の逸脱を検知するテスト・評価器 |
| Mutation | 合成fixtureで意図的に与える、定義済みの制御変更 |
| Evidence | 誰が・何を・どの条件で・いつ検査し・何が出たかを辿れる記録 |
| baseline | 利用目的に対して事前に選定・固定した比較基準。直近runを自動採用しない |
| 評価義務 | 実行前に宣言するControl×検査/Mutation family×環境×証拠種別の必要項目 |
| Finding | 要求違反、劣化、評価不能または欠損についての根拠付き指摘 |

**ガードレールを意図的に弱めたfixtureで検査が期待どおり失敗することは、検査系が有効な証拠になる。** この期待された失敗を、本来のControlに問題が発生した結果へ混ぜない。逆に、タイムアウトや実行エラーを「検知できた」と扱わない。

## 4. 必須要求

以下のGAH-R01〜GAH-R32をMVPの要求案とする。R01〜R24を補強し、敵対的な反例検討からR25〜R32を追加した。[検討記録](reviews/requirements-adversarial-20260910.md)で根拠と処遇を追跡する。具体の保存方式、API名、CLI構文、Schemaの構造は設計工程で決める。[受入条件](acceptance-criteria.md)は同じ番号のGAH-ACに対応する。

| GAH-R04 | 時間、同時実行数、処理量、許可された外部評価の呼出数・費用に上限を設ける。実行中・予約済み・再試行分も予算へ含め、上限到達時は新規処理を止める。進行中処理の停止・期限・停止確認不能と未完了項目を記録し、停止要求だけで停止完了にしない。費用の見積・確定・不明を区別し、必須上限を守れる根拠が不足する処理は開始しない |

### 検査と結果の取得

| ID | 要求 |
|---|---|
| GAH-R05 | 検査開始・終了、対象、実行条件、評価器の版、結果をEvidenceへ結ぶ。プロセス終了コードや空の結果だけを検査成功の証明にしない。起動失敗・結果欠損・構造不正は区別して記録する |
| GAH-R06 | Mutation検査の前提として、同じ目的・検査条件で変更前fixtureが所期の結果を出したことを確認する。前提が失敗・不明なら、そのMutationを検知成功へ数えない |
| GAH-R07 | Mutationの成立、対象検査への到達、所期の検知を区別する。§5のKILLED/SURVIVED/NO_COVERAGE/ERROR/除外を保存し、関係のない失敗や全体クラッシュをKILLEDにしない |
| GAH-R08 | MVPでgeneric commandとPromptfooの結果をadapter経由で取り込めるようにする。対象は許可された固定ケース・合成fixtureに限定し、形式不正・未対応版・実行失敗・判定不能を正規化する。ツールのPASSを無検査でGAHの合格へ変換しない |

### 計測と判定

| ID | 要求 |
|---|---|
| GAH-R09 | 利用目的に適用する指標を分子分母付きで示す。UC-CIの検査系評価ではMutation Score、UC-LLMではTP/FP/TN/FN、検出率・見逃し率・FPRを必須とし、ASRは結果としての逸脱を評価する場合に別計測する。§6に従い未確定数・除外数を併記し、0分母・欠損・未実行を0%や100%の成功値にしない |

| GAH-R11 | baselineと現在の比較条件を検証し、§6の条件を満たす場合だけ差分を出す。比較不能時は現在値、欠ける条件、比較不能の理由を示し、「劣化なし」と表示しない |

| GAH-R13 | Evidenceの鮮度と有効性を判定時点で確認する。期限切れ、対象・条件の不一致、撤回・失効した証拠を現在の合格根拠に使わない。過去の観測結果と現在の利用可否は別に残す |
| GAH-R14 | HOLD時はGAHが管理する新たな非許可処理・合格扱いを止め、CIへ不合格を返す。Evidenceの読取り、診断、範囲内の再検査は継続できる。本番停止や外部サービスへの強制力を持つと表示しない |

## 5. 個別検査とMutationの結果

個別検査の観測はPASS、FAIL、INDETERMINATE、NOT_RUN、ERRORを区別する。STALEは証拠を現在利用できない状態として扱い、過去のPASS記録自体を書き換えない。これらは製品APIのenum確定ではなく、失ってはいけない意味の区別である。

「必須ケース」は評価を完了する義務であり、その全件が正答する条件とは限らない。UC-LLMのFP/FNはまず観測した分類結果として記録する。集合のFPR・検出率で合否を決めるケースと、一件でも違反すれば停止する事象の条件を評価契約で分ける。後者の違反は集合の許容率で相殺できない。前者は許容率内の誤りだけで無条件にDEGRADEDへ変換しない。

予定する評価単位はケースIDと試行IDで識別する。同一試行の再配送と、新しい独立した試行を分ける。応答欠損、認めていないケース、部分出力、結果の矛盾は成功へ補完しない。欠損・除外・再試行を含む全予定数と実行数を示し、固定した採用規則で集計する。規則外の再実行で過去の違反を消せない。

| Mutation結果 | 必要な根拠 |
|---|---|
| KILLED | 変更前の所期結果、Mutation成立、関連する検査が所期の異常を検出した結果が揃う |
| SURVIVED | 前提・Mutation成立・対象への到達が確認でき、期待した異常検知がなかった |
| NO_COVERAGE | 有効なMutationに対する必要な検査が対象へ到達していないことを確認できた |
| ERROR | 起動失敗、タイムアウト、結果不正などで上記の判定ができない。到達の証拠がないだけでNO_COVERAGEへ推測しない |
| 除外 | 同等性・無効性の理由と根拠、対象、判断者を記録したもの。自動で大量除外して成功値を作らない |

Mutation以外の通常検査のFAILと、Mutationで期待する検査失敗は別の文脈として集計する。変更前検査の不成立、ERROR、除外未確定は検知成功ではなく、該当する必須の評価義務を未充足にする。

## 6. 指標、coverage、baseline

### 指標の計数

UC-LLMでは「要検知」を正例、「正常」を負例とする。対象ガードレールが検知した場合を陽性とし、TPは正例の検知、FNは正例の見逃し、FPは正常ケースの誤検知、TNは正常ケースを検知しなかった結果である。検知と実際の遮断は別に記録し、遮断の成否を評価する場合は期待する操作・出力も事前に定義する。

| 指標 | 要求する計算と表示 |
|---|---|
| 検出率（Recall/TPR） | TP / (TP + FN)。要検知ケースをどれだけ検知できたか |
| 見逃し率（FNR） | FN / (TP + FN)。同じ確定済みケース集合では1 − 検出率 |
| 誤検知率（FPR） | FP / (FP + TN)。正常ケースを誤って検知した割合。誤遮断を測る場合は検知と混ぜず別の結果として示す |
| ASR | 事前定義した逸脱結果が成立した数 / 判定可能な有効な逸脱評価ケース数。検知の有無と逸脱の成立は異なるため、ASRを自動的に1 − 検出率としない |
| Mutation Score | KILLED / (KILLED + SURVIVED + NO_COVERAGE)。根拠付きの除外は分母から外すが、除外数・理由とERROR数を併記する |
| Coverage | 固定した評価義務のうち有効な証拠で充足した数 / 必要数。Criticalは対象義務すべての充足が必要。FAILの証拠が存在してもControlが安全という意味ではない |

UC-LLMの評価データにはケースID、期待ラベル、根拠・由来、カテゴリ、版・digestを付け、評価前に固定する。期待ラベルを対象ガードレール自身の今回の回答から作らない。評価器を使う場合も、その版・判定規則・校正根拠を別に識別する。ラベル不明、曖昧な応答、未実行、ERRORはTP/FP/TN/FNに押し込まず、件数と理由を別表示し、該当する必須評価の欠損として扱う。

全体と事前に必須としたカテゴリ別の件数・指標を示す。正常/要検知の比率やケース数が変わった集計を、同一条件の性能変化として扱わない。繰返し測定ではケース数と試行数を分け、集計単位・反復回数・モデル設定・利用可能なseedを固定する。観測された差と統計的に確かな劣化を区別し、必要な標本数・ばらつきの判定規則が満たせない場合は確かな改善や劣化と断定しない。

同じケースの反復や派生ケースを独立した標本として水増ししない。受入用集合を閲覧・調整に利用した履歴、重複と派生グループ、カテゴリごとの件数を記録する。独立性や利用履歴が不明なら、そのデータからの一般化を主張しない。固定した合成ケース上の回帰確認自体は、その限定された目的を明示して利用できる。

合成fixtureの有限集合を数える受入では、確定した件数に対して条件を判定できる。母集団の性能推定を必須とする評価では、点推定値だけで合格にしない。閾値や許容劣化幅をまたぐ不確かさは評価不能とする。手法・信頼水準・片側/両側・対応のある比較・カテゴリの多重比較・途中停止の扱いは事前に決め、結果を見て有利な方式に切り替えない。判定法の具体選定は評価設計に残す。

0分母は「評価不能」。開始前に目的との無関係を宣言した指標のみ「対象外」とし、欠損を対象外へ変更しない。必要な指標や評価義務が評価不能ならHEALTHYへ進めない。対象Criticalが0件の場合は「Critical対象なし」と表示し、Critical coverage 100%と宣伝しない。

元原稿の10 Control・5 Mutation family・2 adapterはMVP全体の受入用データの規模案として維持し、各利用場面・各runに同じ件数を要求するものではない。UC-LLMには正常と要検知の両群が必要である。検出率・見逃し率・FPR・ASRの許容値、Mutation Scoreのリスク別閾値、費用・時間の上限は利用目的に応じた設定値であり、原稿の仮値を本番既定値へ昇格しない。必須の設定が不足すれば入力不成立とし、検査を開始しない。

### 比較条件

比較では、検査集合・Mutation集合・evaluatorと設定・budget・環境・判定方針を識別して固定する。変更を評価したい対象（例: ガードレールの版）は差分として事前宣言し、baselineとcandidate双方の識別情報を残す。宣言していない条件差を無視して比較しない。

UC-LLMではモデル・プロンプト・検出器の設定等のうち何を変更したかを明示する。期待ラベル、判定oracle、ケース構成、反復・集計条件まで同時に変わった結果は、対象だけの性能差として比較しない。評価器自体を評価対象とする場合も、別に固定した期待結果を必要とする。基準を改訂する場合は別版として選定理由を残し、過去との比較不能を隠さない。

比較可否は事前の比較契約に従って指標・カテゴリごとに判定する。正例集合だけが同一でも、共通の評価器や状態の差があれば検出率まで比較可能とはしない。比較可能な部分の差分は表示できるが、比較不能の必須部分を外して全体合格にしない。可変のモデル名・パスだけを版とみなさず、取得可能な実体版や内容識別子を記録し、同一性が不明ならその比較根拠を不足として示す。

baselineの欠如や比較条件の不一致は「比較不能」。現在値は残すが、継続的な劣化検知に必要な比較が欠ければHEALTHYにしない。初回のbaseline候補作成は別の評価目的として表示し、「以前より劣化していない」とは主張しない。

baseline候補作成の目的では、比較を事前に対象外とし、現在の絶対条件・評価器の校正・必要証拠の充足からAssuranceを算定する。全条件を満たせばこの限定目的でHEALTHYとなり得る。作成完了と採択を分け、合格判定に用いるbaselineは比較を除く必須条件と根拠を確認して採択する。既知の違反があるデータを診断用の参照に使う場合も、その用途を分ける。候補作成のHEALTHYを通常の劣化検知CIの成功として代用しない。

絶対閾値・差分・比率条件の適用は実行前の方針へ固定する。baselineが0の比率は計算不能とし、無断で別の条件に切り替えない。絶対値や絶対差は適用可能な条件として別に扱う。条件ごとの成立・不成立・計算不能を残す。

## 7. Assurance状態とCIへの返却

実行が終了したことと、対象のAssuranceが良好なことを分ける。以下は優先順に適用し、優先しなかった理由も捨てない。

| 優先 | 状態 | 条件 |
|---|---|---|
| 1 | HOLD | 入力・権限境界・証拠整合性の不成立、Criticalの違反または必要評価の欠損・ERROR・期限切れ、禁止された副作用などの停止条件がある |
| 2 | DEGRADED | HOLDではなく、必須検査の違反や適用閾値に反する既知の劣化がある |
| 3 | UNKNOWN | 上記でなく、必須評価・比較・指標の不足により判断できない |
| 4 | WARNING | 必須条件は満たすが、事前に任意とした項目の欠損・注意条件がある |
| 5 | HEALTHY | 必須の評価義務と方針を満たし、適用範囲内に上記の問題がない |

Criticalを実行後に非Criticalや任意へ変更してHOLDを解除しない。結果が揃わない場合も、すでに判明したCritical違反をUNKNOWNで隠さない。

両方を対象とするrunではUC-CIとUC-LLMの状態・理由をそれぞれ表示し、全体へ同じ優先規則を適用する。一方のHEALTHYで他方の劣化・欠損を相殺しない。UC-LLMではFPRが改善しても検出率の必須条件に違反した場合は、その違反を判定に残す。単一の総合点だけで合格にしない。

§5の事象ごとの必須条件違反と、集合に対する指標条件の違反をこの表へ入力する。推定性能の根拠だけが不足する場合はUNKNOWN、Criticalに必要な根拠ならHOLDとする。別に確定した必須違反があれば、UNKNOWNで隠さず優先順を適用する。

MVPの標準CI方針案は、評価契約が要求する目的・対象内容・範囲・版に一致し、実行が完了し、必要な結果・Finding・計画の出力が成立し、AssuranceがHEALTHYの場合だけ成功にする。出力が壊れたrunや別目的のrunは、判定値だけがHEALTHYでもCI成功にしない。WARNINGも成功へ緩和しない保守的な案であり、利用者の運用判断として[未決定事項](open-questions.md)に明記する。具体の終了コードとCI接続方法は設計時に決める。

GAHが返せるのは自身の処理制御とCI向け結果まで。デプロイを止める強制力は呼出側のCI/保護設定に依存し、GAH導入だけで本番保護が成立したと扱わない。HOLDは許可範囲内の診断・再検査を妨げない。再検査の結果と証拠の回復をもって再判定し、statusの手書き変更で解除しない。

## 8. 証拠の有効期間と計画の成立条件

証拠には観測時刻と収集時刻を区別して記録する。鮮度は判定時刻から観測時刻までの経過で判定し、再取込みで寿命を延長しない。許容年齢の境界は経過が上限以下なら有効、超過なら期限切れとする要求案。未来の観測時刻や時刻根拠が不明なものは合格根拠にしない。

結果の有効期限は依存する必要証拠のうち最も早い期限を超えない。期限前でも入力版・方針・必要証拠の失効があれば再確認を要求する。MVPは照会・判定時の確認とCIによる定期再評価を対象とし、常駐監視による即時検知の時間保証は行わない。

保存結果の再取込み・キャッシュ読出しは新しい観測ではない。再実行で新しい観測を得た場合だけ別Evidenceとして記録でき、旧Evidenceの時刻や過去の結果は変更しない。新結果の存在だけで別の契約・対象へ紐付く古い違反を解消しない。CI等の利用側でも、参照する結果の対象内容・契約・鮮度を利用時に照合できる情報を出す。

修復計画の成立とは、必要な項目と参照が整合し、既知の根拠と不足事項を区別できること。修復の正しさ・承認・実行可能性を保証するものではない。復旧先が未定ならその不足を明記し、架空の既知正常版を補わない。証拠参照切れや要求と矛盾する計画は「要修正」とする。Findingがない場合は計画不要の理由を示し、架空の修復計画を生成しない。

Assuranceと計画の生成状態は分ける。任意の計画補助LLMが失敗しても定型の計画骨子と不足情報が成立すればGAH-R17を満たし、その補助の成否だけでは証拠に基づくAssuranceを変更しない。評価対象LLMや必須評価器の失敗は別であり、必要な評価の欠損として§7で判定する。必要な成果物の生成まで失敗した場合は、Assuranceとは別に実行不完了を表示し、CI成功にしない。

## 9. 受入と次工程

MVPの要求受入は[32件の受入条件](acceptance-criteria.md)で具体化する。これらは今後の製品試験の期待結果であり、現在のテスト実績ではない。原稿の17機能・14受入項目の処遇は[対応表](requirements-traceability.md)で追跡する。

二つの初期利用場面は確認済み。仕様化前に、標準CIの扱い、利用場面ごとの運用閾値・予算、期待ラベル付き評価データとbaselineを確認する。外部参照元再利用境界、SchemaやCLI構文・保存方式は設計の決定事項として残す。未復元の外部出典と新規性・制度の主張は要求の成立根拠から分離し、[調査原稿](research/README.md)に保存する。

## 10. 信頼の前提と拡張の境界

MVPは、評価契約とGAH実行・保存領域を管理する主体が信頼でき、candidateや評価データがそれらの権限を持たない構成を前提とする。この分離を用意できない実行では、その境界を根拠とする合格を出さない。同じ管理者権限で契約・実行環境・保存証拠をすべて変更できる主体に対する完全な改竄検知は、ローカルdigestだけでは保証しない。

候補が検査・評価器・契約を変える場合は、それも評価対象の差分として示す。既存契約での検証と新契約の採択を分け、候補の自己採点だけで変更を通さない。委任先・外部モデルを使う際も同じ境界、予算、版、根拠の要求を適用する。

変更提案や計画中の記述はデータとして保存できるが、それだけで採択・実行しない。補助LLMが提案を妥当と説明しても権限の証明にはならない。定型の計画骨子を含む全ての説明出力を、評価契約や判定を変更する権限として扱わない。

R25〜R32の最小機能をMVPへ追加し、実運用データへの拡張、評価集合更新時の比較、多様な対話・出力形式、運用上の有用性、署名・外部検証などは[拡張案](extension-roadmap.md)で優先順位と着手条件を管理する。後期候補を未実装のままMVPの検証実績に含めない。
