# 契約・評価設計 v0.3

[要求v0.4](requirements.md)の32要求と[初期運用方針v1](operating-policy.md)から、MVPの論理構成と境界を具体化した。基本設計v0.3を保ち、判定・永続化・診断CLIは[詳細仕様v1](detail-spec.md)で初期実装した。全MVPの正式Schema、外部adapter、管理AI認証・隔離は未接続。[仕様](spec.md)、[契約](contracts/evaluation-contract.md)、[評価設計](contracts/evaluation-design.md)を合わせて読む。

## 1. 構成と責任

GAH内に次の責任を置く。外部資産の抽出や共通coreの分離は前提にせず、共有libraryの分離は実装後の必要性で判断する。[独立設計と非掲載方針](reference-boundary.md)を全成果物へ適用する。

| 責任 | 入力 → 出力 | 保護する境界 |
|---|---|---|
| 契約管理 | 管理AIの提案・根拠 → 採択記録と不変の契約版 | candidateの書込み禁止、権限検証、初期値の下限/上限、世代の競合検査 |
| Control Registry・影響解析 | 採択契約・対象差分 → 対象と必要根拠の閉包 | 循環・参照欠落拒否、影響不明時の限定成功禁止 |
| 実行監督・予算台帳 | 固定run・予定試行 → 実行イベント・停止確認・費用 | 隔離と入出力先、子処理を含む上限、再試行、採択済み領域への書込み禁止 |
| adapter・結果照合 | 許可済み実行の出力 → 正規化結果 | 出力をデータとして解析、予定外・矛盾・版不明・欠損を区別 |
| Evidence保存 | 観測・結果・出典 → 内容識別子付きの記録 | 観測時刻と取込み時刻の分離、撤回、保存完了、履歴を上書きしない |
| 判定・Decay Detection | 契約・正規化結果・基準・判定時刻 → 指標、理由、Assurance | 決定的な判定、部分比較、Critical優先、対象と鮮度の照合 |
| Finding・Remediation Planner | 理由と有効根拠 → Finding・計画・不足情報 | 説明から権限を追加しない、計画生成と修復確認を分離 |
| CI結果出力 | 同じ判定と保存済み成果物 → JSON要約・人間向け要約・終了コード | 成功条件の照合、別目的・旧内容・部分出力の成功禁止 |

Mutation CIは実行監督・adapter・判定を組み合わせ、宣言済みの合成fixtureの変化だけを評価する。一般の対象を探索して改変する機能は設計しない。

## 2. 一つのrunの流れ

1. 呼出側の期待する目的・内容digest・範囲を受け取る。候補の自己申告だけで期待値を決めない。
2. 採択済み契約を解決する。初回だけは配布物に固定したBootstrapContractを用いる。版、必須義務、基準、校正、データ用途、依存閉包、予算、実行境界を検査する。
3. ケース・試行・段階と必要出力を固定し、実行に必要な予算を予約する。見積で収まらなければ実行前に拒否する。
4. 各試行を分離して実行し、監督側が起動・到達・終了・資源利用を観測する。結果を照合して保存する。
5. 観測の整合、欠損、鮮度、指標、比較、個別の禁止条件を判定し、理由を残す。必要なFindingと計画を作る。
6. 必要成果物の保存・精算・停止状態・証拠の有効性・残り時間を再確認し、最終receiptを確定する。CI利用時には現在の失効台帳と期待bindingも照合する。

初回baseline候補作成は比較不要の別目的。通常CIへ代用しない。既知の違反を含む診断用資料と、成功基準として採択できるbaselineを分ける。

## 3. 生成AIの管理と初回採択

管理AIは常設の論理主体として、許可範囲内の契約・検査集合・評価データ・baseline更新を提案し、構造化された採択要求を出す。通常の採択に都度の人間承認を置かない。採択の適用は固定した検査を行う管理境界が担う。

実行identityは管理境界が認証した主体に結び付ける。JSONの`actor_id`やモデルの説明だけでは認証にならない。同じモデルでもcandidateと管理AIのcontext、credential、書込み先を分ける。ホスト管理者に対する完全な改竄防止はローカルdigestでは保証しない。

初回は、GAHの配布物に含める初期方針・固定受入検査・BootstrapContractを管理境界の信頼起点にする。管理AIが自分の提案中のルールを信頼起点へ昇格させない。初回のみ旧契約評価が存在しない理由を記録し、初期方針で全必須絶対条件・校正・根拠を検査する。基準がまだない通常CIは不成功のままにする。初期校正から契約・baseline採択への順序は[LC01](contracts/lifecycle-contract.md#lc01-初回の信頼起点)に従う。

更新は旧契約による評価と差分、新契約の受入根拠を保存する。評価集合や評価器を変えた場合は比較不能を明示し、同じ対象を旧条件でも評価できない理由を黙って省略しない。既知の違反を解決していない変更は元のFindingを修復済みにしない。

採択要求は期待する現行世代を持ち、同じ対象系列の更新を一つずつ適用する。確定点で権限・方針・提案内容・根拠の鮮度と失効状態も再検査する。同じ要求ID・同じ内容の再配送は閲覧権限を確認して過去のreceiptを返すだけとし、現在の有効性を復活させない。内容の違う再配送や古い世代は拒否し、新しい世代へ付け替えない。詳細は[LC02](contracts/lifecycle-contract.md#lc02-採択の確定時検査)。実行中のrunは固定した旧版のまま完了し、新しい版で過去を上書きしない。

## 4. 保存と障害

不変artifactと、現在採択されている版を指す小さな可変参照を分ける。artifactには版、内容digest、生成主体、元のrunを付ける。受入・採択・取消し・撤回は別イベントとして記録する。保存の原子性、世代更新、同時実行時の予算予約を同じ実装で検証してから並行運用を有効にする。

最終receiptは必要artifactが保存・再読込照合できた後にだけ確定する。receiptのないディレクトリ、途中まで書いたJSON、stdoutの成功文字列は完了結果ではない。保存障害時はstderrと非ゼロ終了で失敗を返し、存在しないEvidence参照を補わない。保存方式の製品選定は次の実装準備Taskで決める。

再現には正規化結果、契約版、方針版、判定時刻、参照した証拠の有効性状態を固定する。後日の照会では新しい照会時刻と撤回状態で再判定し、当時の再現結果と現在利用可能な結果を別表示する。

v0.2では[再検討で確認した欠落](reviews/design-review-20260911.md)を補正した。保存済みreceiptを履歴として保ち、保存後の矛盾・撤回は失効台帳とUseDecisionへ反映する。run時間には成果物の最終保存を含み、費用未確定・子処理停止未確認を残した成功は確定しない。並列枠と経過時間は累積消費とは別の規則で管理する。

v0.3では[複合条件の見直し](reviews/state-review-20260911.md)から、初回の循環回避、採択確定時の再検査、再開後の所有世代と元のdeadline、微小課金の切上げ、保存/送信前のデータ検査、終了状態の優先順を[補足契約](contracts/lifecycle-contract.md)へ具体化した。要求・受入条件・初期値は維持し、実装方式の決定や製品試験は次工程に残す。

## 5. 実装へ渡す順序

1. 正式Schema、正規化とdigest、保存・原子的更新方式を決め、[設計の境界例](contracts/decision-examples.v1.json)を実行可能な契約試験へ変換する。
2. 外部実行を伴わない判定・照合・予算予約・Evidence再判定を実装する。
3. 認証と隔離を検証し、合成fixture専用runner・generic command adapterを接続する。
4. 公開原典と固定版を確認してPromptfoo adapterを設計・実装する。対応版や出力fieldを現段階では推測しない。
5. 両UCのfixture、管理AI採択、CI binding、全対象評価を接続して32受入条件を実施する。

現行要求を増やす必要がある事項は、新しい要求改訂として追跡する。設計の詳細化だけで要求や初期値を緩めない。判断の根拠は[ADR 0002](ADR/0002-contract-boundaries.md)、未決定の実装事項は[判断事項](open-questions.md)に残す。
